The strongest candidates I found are:

c1a21bb8 — vo_gpu invalid component overwrite protection. Good robustness fix for custom shaders. Very attractive because it fixes malformed hook/component cases without changing intended rendering.

7d1a598b — vo_gpu PARAMs inside RPN expressions. This is especially valuable for Shader Lab. Parameters could drive conditional shader logic directly instead of us having to encode every behavior in Kotlin/Lua.

3e0729eb — ENUM shader parameters and a0b62333 — DEFINE parameters. These could eventually give us proper discrete modes/toggles—quality modes, algorithms, clipping displays, gamut strategies—inside one resident shader rather than separate shader variants.

11b2004b — scaling-option inheritance fix. mpv could silently ignore certain cscale-*/dscale-* overrides when kernels were inherited from scale. Since image fidelity is a major goal, I want this audited against our Pixel scaling configuration.

702abfd5 — use actual Vulkan texture dimensions. Fixes texture-size mismatches that can cause glitches with polar scalers. Potentially useful for a Vulkan-quality path, although I’d test relevance carefully with mediacodec-copy.

7eb1ef2f — resizable filter windows / proper tscale-radius. Worth having if we later optimize motion/interpolation quality.

There are also newer libplacebo Vulkan synchronization, texture-transfer, swapchain-format, and memory fixes from 2026. Some are genuinely excellent, but I would hold those for a separate renderer-upgrade experiment, because moving from R07’s v7.360.0-3-gc93aa134 to a newer libplacebo already changed the picture perceptibly.

3e0729eb + a0b62333 — ENUM and DEFINE PARAM types. These are very attractive for future quality-mode selectors, gamut algorithms, diagnostic overlays, clipping modes, and boolean feature switches without shader-file swapping.

7eb1ef2f — proper resizable filter windows / tscale-radius. Not immediately necessary, but valuable if we later expose motion scaling/interpolation tuning.

7f72f64b — VO declares total referenced-frame requirements. This is primarily aimed at frame queues/hardware surface pools. It may eventually improve reliability with hardware decoding, although it matters more to gpu-next than our current path.

There are also some libplacebo fixes newer than our exact R07 c93aa134 baseline that I would consider backporting individually instead of upgrading libplacebo wholesale:

3dd24a5 — fixes Vulkan texture transfers when an offset is used.

Highest-value additions for our exact vo=gpu path

1. c1a21bb8 — protect shader-hook component overwrites

This is almost tailor-made for Shader Lab. If a custom hook tries to overwrite something like LUMA with more components than that target can support, mpv now rejects the hook instead of letting the bad configuration continue through the renderer. The patch is localized to vo_gpu/video.c.

Verdict: TAKE. Low visual-risk, high robustness.

2. 8d04be2b — correct Vulkan image-stride alignment

This changes image allocation so stride is aligned to both the requested alignment and the actual bytes-per-pixel requirement. The upstream reason is specifically that Vulkan transfer sizes are expressed in texels.

This is the kind of invisible correctness fix I like for the Pixel renderer: it shouldn't intentionally alter the image, but it removes a class of malformed transfer/layout situations.

Verdict: TAKE, after renderer parity is restored.

There is actually a second-stage PARAM stack upstream beyond the basic support we already backported.

3. a0b62333 — DEFINE parameters

A PARAM can become a GLSL preprocessor define usable inside #if branches.

Very useful for things such as:

diagnostic code on/off

alternate algorithms

clipping visualization

expensive optional passes

compile-time quality modes

But I would not use DEFINE for rapidly adjusted controls. Changing a preprocessor define changes shader source and can require recompilation—the exact thing R08 is trying to eliminate from slider tuning.
